## Migration sequence and invariants

1. Preserve the complete v0.3 source/package and use the isolated v0.4 working directory. Never run tests against a user's live database.
2. Inspect the selected Supabase project's schemas, extensions, migrations, auth configuration, RLS/grants, existing users, and environment purpose before preparing a deployable migration. Do not create a replacement project or guess the target.
3. Take verified encrypted migration snapshots before local changes; take independent remote exports before remote changes. Migration failure must leave the prior database recoverable.
4. Retain all existing local numeric IDs, permanent asset codes, identifiers, and audit entries. Add stable global IDs and explicit legacy-to-cloud mappings; do not renumber old assets. Never upload local password hashes or treat an existing local Admin account as proof of cloud Admin status.
5. A designated cloud Admin explicitly enrolls the initial dataset. Reconcile counts, asset identifiers, audit history, and relation mappings before marking it synchronized. Other devices download that dataset; they do not independently reseed it.
6. New offline assets need globally collision-resistant identifiers/codes. Existing numeric sequences cannot safely be allocated independently on multiple devices. Legacy codes remain unchanged.

## Authentication and authorization

Supabase Auth owns cloud identity. Public signup always creates a Viewer profile, ignoring user-editable role metadata. Only a server-authorized Admin can change roles; preserve at least one active Admin and audit role changes. Bootstrap the first Admin through a trusted administrative procedure after confirming the intended identity.

Enable RLS on all exposed tables and use explicit grants. Permissions must apply server-side, not merely hide UI controls. Read permissions are scoped to the intended inventory/workspace; public signup must not accidentally grant access to unrelated data. Whether self-registered Viewers immediately see this organization's inventory must be confirmed against the connected project's policy.

The Windows app carries only a publishable key. No service-role key, management token, database password, or backup encryption secret belongs in a GitHub release. Protect refresh tokens locally with DPAPI, clear sessions on logout, and re-check the current server role for every write. Local v0.3 passwords remain valid only for the legacy local inventory until explicit enrollment.

## Offline synchronization

Keep encrypted local storage as a working cache. Every accepted local mutation and its outbox message must commit in the same SQLite transaction. An operation has an immutable UUID, actor, entity ID, expected server version, and payload. Server application and operation receipt must commit atomically. A lost acknowledgement can then be retried without applying twice.

Run one sync worker at a time after saves, startup, and reconnection, with bounded retries/backoff. Download remote changes using a server cursor; never infer synchronization from local clock order. Do not overwrite pending local edits during pulls. Flag version conflicts and retain both versions for explicit resolution; no silent last-write-wins.

Offline edits are provisional. Revocations cannot reach a disconnected device; reconnect must reauthenticate and reject now-unauthorized uploads without deleting the local work. First-time login/registration requires internet. Distinguish connection failures, expired login, authorization errors, and conflict responses.

## Duplicate prevention

Check for similar item/location records before accepting a batch. Default/focused action is Periksa Kembali, also used for Escape/window close. Place Tetap Tambah on the opposite side, available only to Editor/Admin. Record actor, matching assets, batch/operation ID, and override decision in the same transaction as asset creation. Repeat server-side checks to catch another device creating a similar record after the local preview.

## Backup and recovery

Create encrypted, compressed local backups for changed sessions, with a persisted dirty marker so crashes are detected at next startup. Keep bounded retention; rotate only after the new backup has been verified. Snapshot before migrations. Automatic backups use a protected local recovery key; manual portable backups require a user-held password and must support another installation. Keep backups outside the replaceable binary folder.

Independent Supabase exports must include database schema/data/roles needed for recovery, audit data, and an explicit Auth/Storage recovery policy. A client-side list export is not a full Supabase backup. Test restoration in an isolated database and reconcile identity/audit counts before claiming recoverability.

## Distribution and service recovery

Use the selected GitHub repository for review prereleases. Build/test/package through a reproducible Windows workflow. Check releases automatically but do not install unverified downloads or overwrite a running app. Updates retain data/config/keys outside versioned binaries, create a recovery snapshot, verify package hashes and expected repository, reject archive traversal, and support rollback. Never ship test fixtures or secrets.

Show connection state and queued/conflicted counts. During outages/pauses continue permitted cached work and show Hubungi Admin with configured contact details. Do not label every network error as a paused Supabase project or automatically resume paid services.

## Review outcome / gates

The main risks identified are legacy code collisions, trusted-client role escalation, duplicate retry writes, stale offline permissions, lost audit attribution, and backups that omit Auth. The mechanisms above are required acceptance gates. Remote SQL and live integration tests remain gated on project inspection; local backup/duplicate implementation and isolated tests can proceed independently.

A v0.4 review release requires demonstrated two-device persistence, duplicate retry suppression, conflict handling, offline/reconnect recovery, Viewer/Editor/Admin denial tests, signup-role tampering tests, local and independent remote restore tests, and update data-preservation tests. No production approval is implied.
